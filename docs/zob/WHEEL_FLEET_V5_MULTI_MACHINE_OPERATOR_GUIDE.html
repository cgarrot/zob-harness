Prepare the fleet without freezing the whole repository

This is the literal zero-effect preparation sequence for reconciled stories and separate physical machines, followed by an honest future-state map of the gates required before any provider-backed edit/test turn, commit, or integration into develop-staging.

Validation and preview available Launch-plan preparation available Provider-backed start blocked Machine-to-story worktree bridge missing Atomic pre-commit authority check missing Live push/PR consumer unavailable develop-staging absent live
Your HEAD concern is valid—and the design does not require one SHA to stay current forever.

The fleet uses a fixed SHA as the admitted starting point for one wave. develop-staging can continue moving as completed work lands. The intended candidate/authority contracts are short-lived bindings for one exact revision, not a permanent repository freeze. The current commit consumer does not yet validate those contracts atomically before mutation, so commit remains unavailable in this guide.

At a glance

What stays identical

  • Wheel/ZOB runtime version
  • Wave bundle and bundle hash
  • Wave sourceSha
  • All referenced story manifests

What is expected to change

  • Each story branch and its local working diff
  • The branch HEAD after a future atomically authorized commit
  • The shared develop-staging tip after merges
  • The next wave’s source SHA and bundle

What is blocked or future

  • Provider-backed run/start and application edits
  • Transferring a machine-worktree diff into the separately required story worktree
  • Synchronizing source between physical machines
  • Push, draft PR, CI observation, or PR-close consumption
  • Staging merge or promotion

Story handoff checks ancestry, not permanent equality.

For PR handoff, the story worktree’s current HEAD must descend from the wave’s sourceSha. It does not have to equal the source forever. See workspace-snapshot.ts. Initial machine claim does not currently enforce source equality or ancestry in code, which is why the explicit pre-start equality check below is a rollout gate rather than optional advice.

In the future enabled workflow, start the dependent story in a later wave from the newer staging SHA. Do not copy a peer’s dirty worktree.
I rebased or changed my branch after making a candidate
In the future enabled workflow, the candidate and authority are intentionally stale. Rerun tests and prepare a new candidate/authority bound to the new HEAD and diff.

Stop. Reconcile from current truth and materialize a new bundle. Do not weaken the ancestor check.
A merge changed the exact commit SHA
That is normal. New commit means new receipt and post-commit lineage. Old receipts remain history, not authority for the new head.

Before the first real multi-machine launch

Do not begin the copy-paste machine steps until all seven boxes are true.

  • The current Wheel/ZOB implementation has been reviewed and published at one immutable full commit SHA. It is currently uncommitted/unreleased.
  • develop-staging has been explicitly created, protected, and proven non-deploying. The live branch check in this session found it absent.
  • reports/wheel-zob/ is intentionally ignored in the application repository. Otherwise launch state makes the worktree dirty and start correctly blocks.
  • The old PR3853 bundle has been rematerialized with the current canonical structured bundle hash after story reconciliation.
  • Initial claim enforces machine HEAD equality to the plan’s sourceSha, and status/local-ready/handoff re-inspect the actual control workspace root, branch, and HEAD instead of trusting persisted metadata alone.
  • A reviewed machine-to-story worktree bridge exists. Today the machine session edits its claimed worktree while PR handoff intentionally requires a different linked story worktree; no automatic hash-preserving transfer connects them.
  • The governed commit tool atomically loads and validates the current Wheel candidate/authority, expiry, branch, workspace, lease, exact diff, and path set before committing. Today it only checks opaque hashes plus current HEAD and validates the Wheel lineage after the effect.
Branch spelling is a contract.

The current schemas and approved design use develop-staging. If the organization chooses dev-staging instead, update the branch policy, manifests, validators, CI, and documentation together before launch. Never use both names casually.

Branch creation, protection, workflow changes, and non-deployment proof are human-controlled architecture work. This guide does not create or push the branch. See Staging Assurance and Promotion Factory and Permissions, acknowledgements, and GitHub Apps.

Target operating pattern after the gates: small waves

After provider-backed start is safely enabled, do not bind all 60 stories to one starting SHA and expect every machine to stay current for days. Reconcile the full backlog, but launch only a small dependency-safe wave at a time.

  1. Choose the wave baseline. Record the exact current develop-staging SHA.
  2. Select only ready stories. Prefer at most one independently committable story per physical machine in a wave. An explicitly approved composite may remain together.
  3. Materialize a wave bundle. Include every story/manifest needed to validate that wave and all dependency references. Every selected machine validates the entire wave bundle.
  4. Future: run the machines in parallel. Each starts from the same wave source SHA but works only its assigned branch and scope.
  5. Finish, review, and integrate one PR at a time. Full staging CI runs against each new staging head.
  6. Refresh the next wave. Use the newest accepted staging SHA, rerun drift/audit checks, and materialize a new bundle.
Rollout blocker: the two-worktree bridge is not implemented.

The implemented test path edits its claimed linked worktree. Exact PR handoff deliberately rejects that same root and requires a separate linked story worktree. There is no current command that safely creates the story worktree, moves the exact reviewed diff, and binds it back to the machine claim. Small waves prevent mixed diffs, but they do not by themselves close this gap. Treat the guide below as the desired operating sequence only. Do not execute start-local-machine for a real wave until every gate above is implemented, validated, and independently reviewed.

Future post-start work contract—not executable today

No machine implementation turn is currently authorized.

The current operator boundary ends after zero-effect plan preparation/status. The behavior below becomes available only after all seven rollout gates are implemented, negative-tested, and independently reviewed.

Future machine may do

  • Read its admitted story and approved dependency evidence
  • Edit only assigned source paths
  • Run Node 20 application tests and static checks
  • Perform local QA, independent review, and repairs
  • Write safe evidence refs and hashes

Machine must never do

  • Take another machine’s story
  • Invent a human gate receipt
  • Commit, push, fetch, or mutate GitHub without the later exact consumer
  • Merge, promote, deploy, or access credentials
  • Copy peer dirty worktrees as dependency evidence

Future dependency behavior

  • Artifact-only dependency: verify the exact safe artifact ref and hash; continue only if the manifest allows artifact evidence.
  • Source dependency: wait for the upstream change to be reviewed and integrated, then start the dependent work from a newer wave.
  • Overlap or conflict: stop the affected story rather than silently editing peer-owned scope.

Future local-ready and commit boundary

Local-ready is not reachable in the current operational workflow because provider-backed start is blocked. After source/workspace enforcement is implemented, a future machine may mark local-ready only after its work is tested, independently reviewed, and bound to safe evidence.

Future local-ready still will not authorize commit.

Two additional implementation gaps remain:

  • No current command creates the required separate story worktree and transfers the exact reviewed machine diff while preserving lineage.
  • zob_zcommit_run treats candidate/authority hashes as opaque strings and can commit before Wheel validates expiry, branch, workspace, lease, diff, or paths.

What must exist before commit can be enabled

  1. A reviewed, hash-preserving machine-to-story worktree bridge.
  2. An atomic commit consumer that loads and validates exact Wheel authority before mutation.
  3. Pre-effect checks of expiry, machine claim/lease/epoch, workspace root, branch, HEAD, content/diff hashes, and exact eligible paths.
  4. A negative test proving stale or fabricated bindings create no commit.
  5. A fresh independent oracle PASS with no_ship=false.

The future contract is specified in the canonical launch/handoff runbook; it is not current executable authority.

How completed stories should reach develop-staging

This is the intended integration sequence once the branch and live adapters are implemented and activated. The current local pack stops before these effects.

  1. Push the exact governed commit. Future adapter must consume current post-commit authority and return an idempotent external receipt.
  2. Create a draft PR targeting develop-staging. Never target develop for an ordinary story.
  3. Run PR CI, PR-close, and blind review on the exact current PR head. Any new commit invalidates prior exact-head review evidence.
  4. Merge one qualified PR into staging. The specified future Staging Merge App uses squash merge and expected-head protection.
  5. Run full integration CI on the new staging SHA. Do not start the next staging merge while staging is red.
  6. Refresh dependent waves. Reconcile against the new staging SHA and produce a new source-bound bundle.
If staging moves while a PR is open

That is expected. Check conflicts and branch policy. If the story branch must be refreshed or rebased, rerun validation and regenerate exact candidate/authority/receipt lineage. Never reuse evidence bound to the old head.

Promotion from develop-staging to develop is a separate human-started frozen-candidate process. It is not part of ordinary story execution. Read the staging, assurance, and promotion design.

Future recovery and restart contract

Operational machine recovery is unavailable while provider-backed start is blocked. The implemented journal/checkpoint/lease contract remains test evidence, not permission to start a real wave.

  1. After the source/workspace gate is fixed, recovery must reopen the exact same linked worktree with the exact reviewed runtime.
  2. Status must reinspect the live workspace rather than trust persisted metadata alone.
  3. A live ownership lease must block takeover.
  4. An expired lease may be recovered only with the exact next epoch.

Contract defaults are a 24-hour launch plan, 12-hour ownership lease, and 4-hour PR candidate/authority lifetime.

Never repair recovery by editing report JSON.

The journal is authoritative. Hash, checkpoint, workspace, branch, HEAD, claim, epoch, and lease mismatches must block or use a separately reviewed repair path.

Troubleshooting

“The worktree is dirty during preparation”

Run git status --short. If only reports/wheel-zob/ appears, the application’s ignore policy is missing. Fix that in the reviewed integration source; preserve any other local work. Operational start remains blocked regardless.

“The plan expired”

Prepare a new launch with a new launch ID after revalidating the bundle. Do not rewrite the old plan or reuse its hash.

“The future story branch needs current staging changes”

The current workflow stops before provider-backed start. In the future enabled workflow, refresh through the repository’s approved process, rerun validation, and move materially changed assumptions into a newly reconciled wave.

“One machine needs another machine’s code”

This is a source dependency, not an artifact hint. Integrate the upstream PR into staging first, then launch the dependent story in a later wave from the new staging SHA.

“Can I run all ten stories assigned to one machine in one branch?”

Not today: provider-backed run/start is blocked. In the future workflow, mixed multi-story diffs still cannot honestly become independent story handoffs; prefer one independently committable story per machine/wave.

“Can I merge the old PRs first and reconcile later?”

Not safely. #3817 is enormous and stale, #3853 is far behind with failed checks, and #3859 is partly superseded. Current-truth reconciliation must precede any merge decision.

“Why can’t I continue to machine start?”

The current pack does not atomically enforce the admitted source at start or reinspect workspace/branch/HEAD at later transitions. After that is repaired, the story-worktree bridge, atomic pre-effect commit validation, and external GitHub consumers remain separate gates.
